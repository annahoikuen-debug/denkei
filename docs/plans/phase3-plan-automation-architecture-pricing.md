| 項目 | 内容 |

## 1. 目的とゴール

- 定型的な契約(業務委託・NDA・雇用等)を**テンプレート+差し込み変数+CSV一括送信**で数分・数クリックに短縮する。
- テンプレートに**署名順固定**と**送信前承認ステップ**を持たせ、押し忘れ・記入漏れ・送信事故を防止する。
- **過剰機能を削減**し、「単一PostgreSQL + オブジェクトストレージ + DBローカルジョブキュー」の最小インフラ構成に集約して運用コストを下げる。
- **月額固定3プラン**(無料/スタンダード/ビジネス)+インボイス対応の領収書発行で、中小企業が導入しやすい料金設計を実現する。

### 成功基準
1. テンプレート→変数入力→(承認)→送信→署名→完了が E2E で通過。
2. CSV一括送信が正常行/異常行混在データで期待どおり動作し、行番号付きエラーレポートを出す。
3. 簡素化(Embedding/EE/API v1/組織階層UI)後に既存全テストがグリーン。
4. プラン制限(件数上限)が正しく機能し、上限到達時のアップグレード導線が動作。
5. 単一コンテナ+Postgres+S3構成で負荷テスト(目安: 10,000文書/月相当のバースト)を通過。

## 3. 実装ステップ(1〜36)

### Stage A: テンプレート変数・差し込み(ステップ1〜7)

**ステップ1. ブランチ整備とベースライン計測(想定: 0.5日)**
- 内容: フェーズ3ブランチを作成し、フェーズ1・2の全リグレッションテスト結果をベースライン記録する。
- 対象: 記録のみ(`docs/plans/phase3-baseline.md`)
- 検証: ベースライン文書完成。

**ステップ2. 差し込み変数スキーマの設計(想定: 1日)**
- 内容: `{{取引先名}}` 等の変数をフィールド・テキスト差し込みの両方で扱うスキーマ(Zod)を設計。テキストフィールドの fieldMeta 拡張と、テンプレートレベルの変数定義リスト(名前/型/必須)を定義。
- 対象: `packages/lib/types/field-meta.ts`、テンプレート型定義、設計書
- 検証: Zod パースのユニットテスト(変数名重複・未定義参照の検知)。

**ステップ3. テンプレート編集UIへの変数挿入(想定: 1.5日)**
- 内容: テンプレートエディタに「変数を追加」ボタンを設け、フィールドのプレースホルダとして選択できるようにする。変数は ja ラベルで管理。
- 対象: テンプレート編集UI(`_authenticated+` 配下)、`packages/ui/`
- 検証: E2E(テンプレートに変数付きフィールドを追加→保存→再表示)。

**ステップ4. 差し込みエンジンの実装(想定: 1.5日)**
- 内容: 送信時に変数へ値をバインドする server-only エンジン(未バインド変数の検知・サニタイズ・PDFへの反映)を実装。
- 対象: 新規 `packages/lib/server-only/template/merge.ts` 等
- 検証: Vitest(バインド/未バインド検知/特殊文字エスケープ)+E2E。

**ステップ5. 変数入力フォーム送信フロー(想定: 1.5日)**
- 内容: テンプレートから「新規送信」した際、変数定義から入力フォームを自動生成する画面を追加(フェーズ1ウィザードのステップ間に挿入)。
- 対象: `_authenticated+/new/`、テンプレート送信ルート
- 検証: E2E(テンプレート選択→変数入力→送信→PDFに値が反映)。

**ステップ6. CSV一括送信の拡張(想定: 2日)**
- 内容: 既存 `bulk-send-template` ジョブを差し込み変数対応に拡張。CSV スキーマ(Zod)検証、行単位の非同期送信、部分失敗の継続ポリシーを定義。
- 対象: `packages/lib/jobs/definitions/bulk-send-template*.ts`、CSVパーサ新規
- 検証: Vitest(CSVパース/検証/部分失敗)。

**ステップ7. CSVアップロードUIとエラーレポート(想定: 1日)**
- 内容: CSVアップロード画面(プレビュー+検証結果)。エラーは「行番号+列+理由」の ja レポートで表示し、修正再アップロードを可能にする。
- 対象: `_authenticated+/` テンプレート配下の新規ルート
- 検証: E2E(正常CSV一括送信/異常行混在でエラーレポート表示)。

### Stage B: 署名順固定・承認ステップ(ステップ8〜13)

**ステップ8. 署名順固定の設計(想定: 0.5日)**
- 内容: `DocumentSigningOrder.SEQUENTIAL` を活用し、テンプレート側で「先方→自社」「自社→先方」の順序を固定設定できる仕様を設計(送信時の変更不可オプション)。
- 対象: 設計書、`packages/lib/types/`(テンプレート設定)
- 検証: 設計レビュー完了。

**ステップ9. テンプレートの署名順固定UI(想定: 1日)**

- 対象: テンプレート設定UI、ウィザード
- 検証: E2E(順序固定テンプレート→送信→先方の署名完了後に自社欄が有効化)。

**ステップ10. 送信前承認ステップの設計とスキーマ(想定: 1日)**

**ステップ11. 承認UIと通知(想定: 1.5日)**
- 内容: 承認依頼通知(jaメール+ダッシュボード)と承認/差し戻し操作UI。差し戻し時は下書きへ戻す。

**ステップ12. 承認の監査ログ(想定: 0.5日)**

**ステップ13. 日本語雛形テンプレートの同梱(想定: 1.5日)**

| E2E | CSV一括送信(正常/異常) | `jp-bulk-send.spec.ts` | 各PR |
| E2E | プランゲート・アップグレード導線 | `jp-plan-gates.spec.ts` | 各PR |
| E2E | API v2 存続確認(v1 廃止後) | 既存 API spec 修正 | 各PR |

### 4.2 既存機能保護(壊してはいけないもの)
- フェーズ1・2で作成した全 spec(コアフロー/ウィザード/モバイル署名/OTP/アクセス制御/リマインダー/ダッシュボード)。
- 既存テンプレート・ダイレクトリンク機能(TemplateDirectLink)の後方互換。
- seal-document・webhook・監査ログハッシュチェーン。
- ストレージ2種・ジョブプロバイダの既存 spec(local 以外はオプトイン維持)。
- v2 API(tRPC OpenAPI)のスキーマ互換(既存 API 連携ユーザー保護)。

### 4.3 CI 組み込み
- PR: lint → tsc → Vitest → E2E(コア+テンプレート+プランゲート)→ 視覚回帰。
- main: E2E フル+負荷テスト(夜間)。
- 削除系PR(案9)は「削除対象の参照チェック」(grep ベースの検査ジョブ)を必須化し、削除後も残る参照を検出。

## 5. リリース計画とロールバック
- 段階リリース: 内部 → ベータ数社 → 全体。新プランは既存ユーザーに事前通知し、締切を設けて移行。
- 削除系変更は「flag で無効化→1リリース観察→物理削除」の2段階。ロールバックは flag 復帰で対応。
- 移行はバックアップ取得→リハーサル→本番→整合チェックの4工程を必須化。

## 6. リスクと対策

| リスク | 対策 |
| --- | --- |
| 差し込み変数の誤バインド(契約内容の取り違え) | 未バインド検知の送信ブロック+差し込み後PDFの目視確認ステップ(オプション) |
| CSV一括での大量誤送信 | 送信前プレビュー確認+上限(同時送信数)+取り消し猶予(送信後5分でキャンセル可能) |
| 削除による OSS コミュニティへの影響 | 削除ではなく flag/ビルド除外で残置し、セルフホスト版では有効化可能に維持 |
| 負荷テストで判明する性能劣化 | ステップ25をリリース前に必須化し、インデックス・並列度の調整枠を確保 |
| 請求書払いの回収リスク | 請求書払いは年払いのみ+審査制とし、未払い時の自動停止フローを整備 |

3. 簡素化後のコードベースで不要参照ゼロ(検査ジョブ通過)。
